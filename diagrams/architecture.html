Architecture review — LUCT CMS / Portal compatibility

Guidance incorporated from LUCT CMS and Student Portal operational experience. Keep the canonical domain clean; concentrate legacy complexity in the CMS anti-corruption boundary (CAP-53). This phase (confirmed 23 Sep 2026): existing Cyberjaya CMS remains System of Record; portals via Portal API; do not duplicate operational desks. Longer term: progressive unified one-stop CMS on verified gaps + migration strategy (target delivery). Ideal (proposed): one product, distributed country databases, white-label and feature flags. Portals never talk to CMS / Postgres / files directly.

Six instructions for documentation authors

  1. Keep the canonical academic model clean — do not copy the legacy schema.
  2. Upgrade CAP-53 from “CMS database adapter” to a documented anti-corruption / integration layer.
  3. Make historical academic state immutable/auditable and calculations reproducible.
  4. Explicitly model statuses, curriculum versions, repeats, transfers, exemptions, and credit/CGPA rules — do not hide them in SQL.
  5. One authoritative owner per domain; cross-system operations must be idempotent, recoverable, and reconcilable.
  6. Assume legacy data is imperfect — detect and expose inconsistencies rather than silently guessing.

Academic model decisions

Keep ProgrammeVersion

Enrolment is pinned to the version under which the student enrolled (e.g. BBA 129 vs 122 credits). Do not resolve requirements from “current” programme config.

ProgrammeCampusOffering (preferred over Faculty-as-campus)

Same programme may be delivered at several campuses while sharing academic identity. Faculty remains organisational; offering is explicit.

flowchart LR
  P[Programme] --> PV[ProgrammeVersion]
  PV --> PCO[ProgrammeCampusOffering]
  PCO --> B[Botswana]
  PCO --> U[Uganda]
  PCO --> S[Sierra Leone]
Mirrors ModuleOffering (module × term × campus). See ERD curriculum. ProgrammeEnrolment.campusId remains the student’s study campus.

Credits earned ≠ credits in CGPA

Retain ModuleResult.includedInCgpa. Pass/elective/exemption cases must be representable without special-case transcript SQL.

Valid example: Grade PASS · Credits earned 3 · CGPA points 0 · Included in CGPA false.

Also support: normal, repeat, exemption, credit transfer, pass/fail, audit/non-credit, replacement, additional elective, transferred programme credit — via registration type + result flags, not ad-hoc SQL.

Calculations are reproducible snapshots

Authoritative inputs: ModuleRegistration + ModuleResult + CurriculumModule + ProgrammeVersion + grading rules. TermResult is a calculated snapshot (calculationVersion, calculatedAt), not primary truth.

ResultPublication versions published academic history

Publication is not only publishedAt on the current row. Corrections create a new publication that supersedes the previous; prior versions remain auditable.

AcademicTerm ≠ student’s programme semester

Keep explicit: calendar AcademicTerm (e.g. 2026-03) vs StudyPeriod.programmeSemesterNumber (Semester 5 for one student, Semester 3 for another).

Attempts are never overwritten

ModuleRegistration.attemptNumber + registrationType. Failed then repeat keeps both rows; policy decides CGPA/credit effect.

AcademicProgressService — policy not transcript SQL

calculateModuleOutcome, credits, term GPA, CGPA, graduation progress, prerequisites. Transcript is a presentation of calculated history. One service — not portal/registry/transcript/stored-proc each inventing rules.

History is never rewritten

Defer / return / transfer / withdraw / re-enrol create or transition records. Use EnrolmentStatusHistory (and similar) for auditability.

Define “active student” properly

EMGS active ≠ CMS registered ≠ current semester ≠ current active report. Avoid one universal student.status = ACTIVE.

Integration operations

LegacyEntityMap

Canonical UUID ↔ sourceCampus + legacyTable + legacyId. Supports overlapping numeric IDs across campuses.

DataQualityIssue + reconciliation

Expect imperfect legacy data. Flag CURRENT_ENROLMENT_WITHOUT_STUDY_PERIOD, LEGACY_PASSPORT_MISMATCH, etc. CAP-53 reports CMS vs mapped counts and domain integrity checks.

Idempotency — IntegrationOperation

Register module, accept offer, create enrolment, submit marks, publish results, invoice, payment, forms — all keyed. Retries must not double-write.

Transaction / workflow states

Registration → CMS → invoice must define failure modes. UI success only when the agreed boundary completes.

flowchart LR
  P[PENDING] --> PR[PROCESSING]
  PR --> C[CMS_COMMITTED]
  C --> F[FINANCE_PENDING]
  F --> OK[COMPLETED]
  PR --> FAIL[FAILED]
  C --> REC[REQUIRES_RECONCILIATION]
  F --> REC

AuditEvent

Who / what / when / why / before / after for marks, grades, registrations, enrolments, finance, publications, visa — not only application logs.

Migration: preserve raw legacy

Legacy source → raw import → mapping/validation → canonical. Never silently “fix” historical academic data on import.

Campus differences = configuration

CampusConfig / CampusPolicy / CampusCmsAdapter. Canonical model stays consistent; no if (campus === "botswana") scattered in domain services.

Identity ≠ legacy password behaviour

IdP → stable subject → Person/Student/Staff mapping. Legacy password/email login stays behind a temporary adapter — not canonical design.

RBAC scopes

Beyond role × method × campus: faculty, programme, module offering, operation. A Botswana lecturer does not automatically see every Botswana student’s marks.

ResultAccessPolicy

Rule-based (campus, funding, balance, holds, term) → allowed + reasonCode. Not hardcoded if (balance < 1000) in the portal.

Integrity constraints (document intentionally)

Examples: unique studentNumber where applicable; unique StudyPeriod(enrolment, term); ModuleResult 1:1 registration; TermResult 1:1 study period; controlled registration uniqueness by attempt; payment allocation limits; offer accept must not create two first enrolments.

Integration health

Beyond API/DB up: adapter latency, failed writes, retry queue, unmapped records, reconciliation mismatches, stuck registrations, file/metadata orphans.
