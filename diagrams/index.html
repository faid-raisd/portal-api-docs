Raisd campus — what we are building

Executive summary

Raisd is modernising how applicants, students, lecturers, and staff use campus systems — without throwing away the working Cyberjaya / LUCT CMS that already holds the official records.

Think of it as four new front doors (Applicant, Student, Lecturer, Staff) that all talk to one Portal API. That API is the only bridge to the existing CMS. Nobody’s browser talks to the database or file store directly.

This phase (confirmed 23 Sep 2026): keep the existing CMS as the system of record; ship better portal experiences; do not rebuild operational desks that already work. Longer term: one unified Raisd CMS with databases placed by country (Malaysia, Singapore, Sierra Leone, Botswana, …), white-labelling, and feature toggles — reached via M5 progressive migration, not a launch rewrite.

  1. Now: student UI is largely demo/mock; applicant / lecturer / staff portals and live CMS writes are still ahead.
  2. Next: agree rules (M1), then admissions end-to-end on real records (M2).
  3. Then: core student journeys (M3), Cyberjaya pilot (M4), other campuses (M5), then distributed ideal.

High-level architecture

Four role portals → Portal API → anti-corruption layer (CAP-53) → existing CMS. Planned Postgres holds portal maps, audit, and session — not a second copy of CMS data. Detail: Architecture review · SDD-02 · ADR-1.

Who uses what

Browsers never talk to CMS, Postgres, or files directly.

Distributed CMS — ideal end state (high level)

End goal: one Raisd CMS product with a database (and preferably API capacity) per country / region, each campus white-labelled and feature-toggled. Global control plane holds tenancy, branding, flags, and identity maps — not student ledgers. Full step-by-step: Distributed CMS architecture.

Current state, target state, and what needs to be done

Baseline product truth: SDD-01. “Demo” on screen is not “Live” — Live needs durable save, real records, and server-enforced permissions.

Current state

  • Student portal: deepest UI, still mostly demo / mock data.
  • Applicant, lecturer, and staff portals: not launched as Live products.
  • Backend: contracts and mock runtime; CMS writes not Live.
  • Auth: mock student session; real SSO / CMS login still ahead.
  • Staff work: continues on the existing LUCT CMS desks.
  • Docs & diagrams: published for the working group (this site).

This-phase target (M1–M4)

  • Four portals on real Cyberjaya CMS records via Portal API.
  • Admissions first, then core student journeys and pilot acceptance.
  • Staff stay on verified old CMS unless a gap is proven.
  • Phone-friendly core journeys (not a native app mandate).
  • Monitoring, backups, privacy, and training ready for Cyberjaya pilot.

What needs to be done

  • Agree campus rules, owners, and API access (M1).
  • Ship Portal API first slice + admissions end-to-end (M2 / CAP-53).
  • Wire Live auth that respects CMS login rules.
  • Make student learning, fees, and support paths Live or keep them on verified old CMS (M3).
  • Complete Cyberjaya pilot acceptance and ops readiness (M4).
  • Only then expand campuses and migrate remaining CMS domains with a written strategy (M5).
Longer-term direction (M5+ → ideal): a progressive unified one-stop CMS — retire legacy desks domain-by-domain when ownership, cutover, rollback, and training are agreed. Ideal end state: one product with distributed country databases, white-label, and feature flags ((one-page architecture)). Not a rewrite mandate for Admissions launch. See target delivery.

Migration stages (M1–M5)

Order is admissions-first. A milestone is when something must work, not when investigation starts. Dates are TBC until the working group locks them. Full plan: Migration · SDD-03.

M1 Confirm rules & integration Campus rules, named owners, legacy capabilities, and API access agreed. Unblocks later work — not a UI release. M2 Admissions launch Apply → evidence → offer → enrol on real records. Portal API first slice. Staff review via verified CMS or new screens. M3 Core student portal Learning, records, fees, and lecturer/staff support paths Live — or still on verified old CMS where that is safer. M4 Cyberjaya pilot acceptance Campus accepts the integrated pilot. Training and operations ready. Hosting at pilot stage. M5 Expansion & remaining CMS Other campuses (e.g. Sierra Leone pattern). Move SoR only with a written migration strategy per domain. Ideal Distributed Raisd CMS One product · country DBs · white-label · feature flags · per-country identity (proposed target).
