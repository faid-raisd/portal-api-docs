Cyberjaya CMS — end-to-end functional flow

Full campus lifecycle for LUCT Cyberjaya (MYS-CYB, DB cmscbj) — the ADR-1 launch system of record. Package CMS_Cyberjaya_Source_Codes_&_DB_Structure_23_09_2026. Campus UI brand [MYS-CYB]. Raisd portals sit in front via Portal API → CAP-53 ACL; staff desks stay on CMS MySQL. Longer-term unified CMS sits under M5+ — not Admissions launch rewrite. PHPMaker core plus Laravel payment/ and icupdpa/.

DB cmscbj ~1942 tables 318 SPs 38 functions 239 triggers 655 views ~20 desks ADR-1 SoR Dump 23 Sep 2026
This phase — ADR-1 (confirmed Aslam, 23 Sep 2026). Use the existing Cyberjaya CMS as system of record. Build modern portal experiences via the Portal API → CAP-53 anti-corruption layer → existing MySQL. Do not duplicate operational staff functions the old CMS already runs. Also seen in dumps: campus2_cyberjaya, portalcyberjaya.
Longer-term target. Still aim for a unified, one-stop CMS, delivered progressively on verified gaps with an explicit migration strategy (ownership, cutover, rollback, training). That consolidation sits under M5+ / remaining-CMS work — not Admissions launch rewrite. See SDD-03 and campus comparison.
Technology shape. PHPMaker core under cyberjaya/campus/<desk>/, plus Laravel sub-apps payment/ and icupdpa/. Live classes use Adobe Connect tables and classroom.limkokwing.net streaming. Batch ops live in cyberbatch/ and CYBERJAYA-SCRIPT/. No TEF / DTEF government scholarship API (that pattern is Botswana-only).
Scope. Structure and behaviour only. PHP tree, credentials, and live student data are not committed. Canonical notes: old-cms-cyberjaya.md, cms-feature-comparison.md. Legacy URLs (comparison, fsd, erd, flows, database) redirect into this hub.

3. Core process flows

3.1 Admissions & registry

3.2 Academic term cycle

ProgramsAllowedToRegister → modules → fees / marks

Atomic with triggers; finish with bursary student refresh.

flowchart TD
  Gate[ProgramsAllowedToRegister] --> Sem[Insert/update r_stdsemester]
  Sem --> Mod[Insert/update r_stdmodule]
  Mod --> Trig[Fees / registration triggers]
  Trig --> Upd[b_Update_Student]
  Upd --> Out[AccOutstanding / CGPA consistency]
  Mod --> Att[r_stdattendance / Adobe]
  Mod --> Mark[b_Update_Student_Mark]

Do not bypass b_Update_Student (and related mark/billing variants) when mutating registration or balances — overnight batch and desk UIs assume these procedures keep outstanding and academic aggregates consistent.

3.3 Finance & payment

Proof → b_paymentverification → receipts

Proof ≠ payment. Bursary verifies; Laravel payment app may issue receipts.

flowchart LR
  Stu[Student uploads proof] --> PV[b_paymentverification]
  PV --> Staff[Bursary review]
  Staff -->|approve| Rec[b_receipt / b_receiptdetail]
  Staff -->|reject| Back[Student notified]
  Rec --> Stmt[b_statement / AccOutstanding]
  PayApp[Laravel payment/] -.-> Rec
