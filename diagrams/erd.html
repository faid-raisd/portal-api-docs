Entity Relationship Diagrams

Logical data model for Raisd campus portals. Attributes and relationships mirror Zod contracts in student-portal and admissions entities from SDD-04. Split by domain so each diagram stays readable.

PK / FK annotated Cardinality explicit Students map via programme version ProgrammeCampusOffering Logical — not a migrated Postgres schema
Student ↔ programme mapping. Students are mapped to a programme version, not only to a programme. Path: StudentProfile → ProgrammeEnrolment → programmeVersionId → ProgrammeVersion → Programme. Keep ProgrammeVersion: enrolment stays on the curriculum/rules under which the student enrolled (e.g. BBA 129 vs 122 credits) — never resolve from “current” programme config. See domain map, student record, and architecture.
Campus where a programme is offered. Prefer ProgrammeCampusOffering (programme version × campus), not “faculty belongs to one campus ⇒ programme belongs to that campus”. The same academic programme may be delivered at Botswana, Uganda, Sierra Leone, etc. Faculty remains organisational. Enrolment still stores ProgrammeEnrolment.campusId for the student’s study campus. See curriculum and architecture.
Canonical vs legacy. Do not mirror r_student / r_stdprogram / … Legacy IDs live in LegacyEntityMap; messy translation lives in the CAP-53 anti-corruption layer. Details: LUCT CMS / Portal compatibility.

Programme version, not programme alone. Path: StudentProfile → ProgrammeEnrolment → programmeVersionId → ProgrammeVersion → Programme. Study periods, module registrations, finance account, visa pass, and most journey records hang off that enrolment. A student may hold more than one enrolment (different programmes or versions over time). Historical enrolments and study periods must be preserved — defer / return / transfer / withdraw create or transition records (EnrolmentStatusHistory), not rewrite academic history. Statuses are layered (identity / enrolment / study period / registration / immigration / finance) — see active student definitions.

5. Registration, progress & results

Module registration is the junction for attendance, submissions, and published results. Attempts are never overwritten. TermResult is a calculated snapshot; published history is versioned via ResultPublication.

ModuleResult 1:1 registration; TermResult 1:1 study period. Credits earned ≠ CGPA inclusion (includedInCgpa).
