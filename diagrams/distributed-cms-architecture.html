Distributed CMS — current milestones → ideal state

One page for the end goal: a single Raisd CMS product with databases and compute placed by country / region (Malaysia, Singapore, Sierra Leone, Botswana, and further campuses), each with its own white-label, feature toggles, and identity — reached step by step from today’s ADR-1 Cyberjaya path through M1–M5.

1. Ideal end state (target architecture)

Raisd ends as one CMS system (one product codebase, one Portal API contract, four role portals) with a distributed data plane: each country or regulated region keeps its own database and may run local API/portal capacity for latency and data residency. Global control-plane services own tenancy, branding, feature flags, and identity federation — not student ledgers.

Logical shape — single product, many country data planes

Portals stay thin. Writes always go to the campus’s local system of record.

Product layer (one)

  • Applicant / Student / Lecturer / Staff portals
  • Portal API (same OpenAPI contract)
  • Raisd CMS domain services (post-legacy)

Control plane (global)

  • Campus / country tenant registry
  • White-label packs (brand, locale, legal copy)
  • Feature flags per campus / country
  • Identity provider mapping

Data plane (per country)

  • Authoritative CMS database
  • Evidence / file store
  • Local Portal API replicas
  • Country compliance batch jobs

Country uniqueness

  • MY: EMGS, MQA/KPT, PTPTN, …
  • SL / BW / others: local QA & fees
  • Toggled modules — not forks
Non-negotiable: one codebase and one CAP catalogue. Country differences are configuration + feature flags + local adapters — not separate CMS products per campus.

What must happen in M1

  • Named owners for CMS access and campus rules
  • Integration credentials for non-production Cyberjaya
  • Confirm which Premium hosts CMS (SDD-12)
  • Close “Needs checking” that unblock Admissions
  • Primary CAP: CAP-42

Why this matters for the ideal state

  • Sister CMS dumps prove country DBs are already isolated
  • CAP catalogue must stay shared across countries
  • Do not force one physical DB for compliance-heavy countries
  • Inventory → adapter map → later Raisd SoR cutover
This phase — ADR-1 M2 Admissions · M3 Core student · M4 Cyberjaya pilot

4. M2–M4 — portals on Cyberjaya CMS (Singapore)

Four portals talk only to the Portal API. Live writes succeed only after the Cyberjaya CMS acknowledges them (CAP-53). Hosting stays on UltaHost Singapore k3s (SDD-12). Staff desks remain on verified old CMS unless a gap is proven.

6. Ideal state — unified Raisd CMS, distributed databases

Legacy campus CMS instances are retired (or reduced to read-only archive). Raisd CMS is the only write path. Each country (or regulated region) runs its own database and preferably local API capacity. Global services never hold the student ledger.

Global control plane + regional data planes + shared portal apps.

Scale-out unit

A country data plane: DB + files + optional API pool. Add a country by provisioning a plane and registering a tenant — not by forking the CMS.

Geo placement

Compute near data for latency and residency. DNS / gateway routes campus → region. Cross-region reads are explicit and rare.

Identity

Each country maps to its IdP / local auth rules. Tokens carry campus_id, country_code, roles. Server enforces scope.

Ops

One release train; per-country config. Backups and restore drills per data plane. Central metrics with country labels.

8. Data plane — residency, sync, and what must never be shared

Distributed database means partition by country / campus, not a single multi-writer global database. Cross-country data movement is exceptional and explicit.

Stays in-country

  • Student master, applications, results, fees
  • Evidence files and payment proofs
  • Staff operational desks and audit for that campus
  • Country-specific regulator extracts

May be global (non-ledger)

  • Tenant registry and feature-flag definitions
  • White-label assets (or CDN copies)
  • Aggregated ops metrics (no PII)
  • Schema version / release metadata
