Canonical Schema v2 may proceed without every LUCT campus agreeing identical operational rules first. Shared vocabulary and invariants stay canonical; campus-dependent behaviour is effective-dated configuration approved before that campus or feature goes Live.

0. Policy hierarchy

Canonical model and invariants are shared. University default policy seeds a sensible baseline. Campus overrides apply where approved practice differs — always with effective dates so policy changes do not rewrite history.

2. Registry (CS-01–CS-04)

Non-blocking for Schema v2. Confirm mappings and policies per campus before Live EMGS / reports / portal narratives for that campus.

ID Decision Canonical / default Live readiness
CS-01 Retain canonical academic statuses active | repeat | outstanding | enrolled | credit-transfer | deferred | inactive | deleted and enrolment lifecycle active | completed | withdrawn | deferred. Legacy → canonical mapping is effective-dated via campus_status_mapping. Fixed invariant: latest academic period from valid ordered study periods — never latest row, ID, or TermID. Demo statuses + status events already in Schema v2. Registry — verify mapping at migration / onboarding per campus
CS-02 One calculation mechanism: active programme enrolment + latest valid study period + term contains reference date + academic status satisfies campus active-student policy. Default seed: {active, repeat, outstanding, enrolled, credit-transfer} via campus_academic_status_policy. Defines academic status only — not Portal authorization (finance / VIP / PTPTN stay in access-policy). SQL view + TypeScript helper in Demo. Registry + International Office (policy); Product (access layer)
CS-03 Keep Outstanding, Deferred, and Inactive as three distinct concepts. Default: Outstanding → valid + active; Deferred / Inactive → not currently active. Do not collapse Inactive into Deferred. Three separate canonical statuses. Registry — campus academic-status policy
CS-04 Keep enrolment baseline active | completed | withdrawn | deferred. Do not add speculative suspended / terminated / transferred-out until a real campus process needs distinct meaning; map legacy values for now and extend the enum later if required. Four statuses + effective-dated status events. Registry / product — only if a campus process requires extension
