Proof of concept · not production

Vercel frontend + Portal API + Neon PostgreSQL

Throwaway / early hosted Demo path for a Raisd portal SPA and Portal API on Vercel, with free Neon Postgres used only by the API. Does not replace UltaHost + k3s (SDD-12 / ADR-2 / ADR-3).

Status: Not started PoC only Portals → Portal API only Neon free tier
Not an ADR. Production remains UltaHost Singapore with k3s. The existing Cyberjaya CMS stays the system of record for Live writes (ADR-1). Do not present this PoC as Live campus architecture. Canonical agent text: docs/ai/architecture/vercel-neon-poc.md.

Goal

Deploy a portal web and the Portal API on Vercel. Neon provides serverless PostgreSQL for PoC session / prototype tables. Bind the SPA with one public API URL env var.

Architecture (PoC only)

Portals still never talk to Postgres or the CMS directly. Only the Portal API may hold DATABASE_URL.

Why Neon on Vercel (2026)

Vercel’s first-party Vercel Postgres has been discontinued. New databases come from Vercel Marketplace (Neon, Supabase, Prisma Postgres, AWS Aurora Postgres, and others). Neon is the simplest free Postgres option for this PoC: Native integration, $0 start, scale-to-zero, branching.

When to prefer Supabase

Choose Supabase from the same Marketplace if the PoC also needs bundled Auth, Storage, Realtime, or Supabase client APIs. For Raisd’s shape (SPA → Portal API → Postgres), prefer Neon.

Free-tier fit for Raisd

Enough for: Demo session tokens, small seed graphs, a handful of concurrent testers, schema branching without claiming Live CMS parity.

Not for: Production cohorts, evidence blobs, CMS ledger replica, treating Neon as Live SoR (contradicts ADR-1), heavy CI against one free project.

Graduation path: keep the Portal API contract; move durable data to SDD-12 Postgres on UltaHost (or CAP-53 CMS adapter). Swap DATABASE_URL / CMS adapter — do not teach the SPA a second data plane.

Implement and deploy

1. Provision Neon from Vercel

Dashboard: Vercel → Marketplace → Neon → Install (attach to the portal-api project).

CLI:

vc i neon/neon

Confirm DATABASE_URL (and any unpooled / branch URLs) appear under the API project’s Environment Variables for Preview and Production. Schema and rows can be inspected from the Vercel dashboard for Neon integrations (2026).

2. Portal API project (Vercel)

  1. Create a Vercel project rooted at portal-api/ (or a thin wrapper).
  2. Adapt the Fastify HTTP entry to Vercel Node serverless / Fluid compute (request-listener adapter or equivalent handler calling the same PortalApi methods).
  3. Set environment:
VariablePurpose
DATABASE_URLNeon (Marketplace-injected)
STUDENT_PORTAL_ROOTOnly if still bridging the mock engine from a packaged path — prefer contracts without a sibling checkout
CORS_ORIGINExact student-portal Vercel origin(s)
NODE_ENVproduction on Production
  1. Keep OpenAPI behaviour: POST /v1/auth/login, POST /v1/portal/{method}. Contract SoT: OpenAPI Swagger.
  2. PoC Neon writes are Demo / Partial until CAP-53 CMS acknowledgement — do not mark Live.

Optional first slice: persist only sessions and scenario id in Neon; leave domain reads on the mock projection until a table plan exists.

3. Student portal project (Vercel)

  1. Second Vercel project from student-portal (Vite → dist/).
  2. Build: npm ci && npm run build (needs NODE_AUTH_TOKEN for @raisd-campus/design-system).
  3. Output directory: dist.
  4. Env: VITE_PORTAL_API_URL=https://<portal-api-project>.vercel.app.
  5. Production builds must use the HTTP PortalApi adapter (no MockPortalApi in the ship bundle).
  6. SPA rewrites so client routes serve index.html.

4. Bind and smoke-test

1. Open student Vercel URL → sign-in Demo scenario
2. Network: POST {VITE_PORTAL_API_URL}/v1/auth/login → 200 + bearer
3. Network: POST .../v1/portal/getDashboard (or getImmigration) → 200 + cms ack
4. Vercel / Neon dashboard: session row present (if sessions persisted)
5. This Pages OpenAPI remains the contract SoT — do not fork openapi.yaml on Vercel

CORS must allow the SPA origin; the current bearer model does not require cookies.

5. Secrets and hygiene

  • Never commit .env, Neon connection strings, or Vercel tokens.
  • Prefer Marketplace-injected DATABASE_URL.
  • Rotate the Neon role if a Preview URL or log leaks the connection string.
  • PoC databases may be wiped; do not store real student PII.

Out of scope

  • Replacing UltaHost / k3s stages or hostnames (apply.raisd.co, api.raisd.co, …).
  • Moving the existing Cyberjaya CMS onto Neon or Vercel.
  • Durable evidence / payment-proof object storage (Live still needs a file store).
  • Staff Live progression APIs (still deferred).
  • Using free-tier Neon as production capacity planning.
