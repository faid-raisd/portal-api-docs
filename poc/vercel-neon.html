Proof of concept · Demo · not production

Vercel frontend + Portal API + Neon PostgreSQL

The hosted Demo of the Raisd portals: four portal webs and the Portal API on Vercel (Singapore), with Neon Postgres used only by the API for sessions. Does not replace UltaHost + k3s (SDD-12 / ADR-2 / ADR-3).

Schema

Every collection of the student-portal PortalRecordGraph is one table, named in snake case (studentProfiles → student_profiles): people, student profiles, programmes and versions, modules, offerings, registrations, class schedules and sessions, attendance, assessments and results, finance accounts, invoices, payments, funding, online forms, immigration, graduation, announcements, campus services and more. The record jsonb is the source of truth; every top-level field is also a read-only generated column so rows are readable in DB admin. 

erDiagram
  RECORD_TABLE {
    text id PK "record id"
    integer position "fixture order"
    jsonb record "source of truth"
    timestamptz updated_at "last write"
    generated fields "one column per top-level field"
  }
  student_portal_state {
    text student_profile_id PK
    jsonb personal_profile
    jsonb resume_profile
    jsonb portfolio_profile
    jsonb finance_payment_proofs
    jsonb chat_store
    timestamptz updated_at
  }
  portal_meta {
    boolean id PK "single row"
    bigint revision "+1 per record write"
    timestamptz seeded_at
    text_array collections
  }
  poc_sessions {
    text token_hash PK "sha256 hex of the bearer token"
    text scenario_id "Demo student scenario"
    text student_profile_id "profile for the scenario"
    timestamptz created_at "default now()"
    timestamptz expires_at "created + 12 h (indexed)"
    timestamptz revoked_at "set on logout, else null"
  }
        
-- one per collection, e.g. invoices
create table if not exists invoices (
  id                 text primary key,
  position           integer not null,
  record             jsonb not null,
  updated_at         timestamptz not null default now(),
  finance_account_id text    generated always as (record->>'financeAccountId') stored,
  total_minor        numeric generated always as ((record->>'totalMinor')::numeric) stored,
  status             text    generated always as (record->>'status') stored
  -- … one column per top-level field
);

create table if not exists poc_sessions (
  token_hash         text primary key,
  scenario_id        text not null,
  student_profile_id text not null,
  created_at         timestamptz not null default now(),
  expires_at         timestamptz not null,
  revoked_at         timestamptz
);
create index if not exists poc_sessions_expires_at on poc_sessions (expires_at);
  • The raw token is never stored — only its SHA-256 hash, so a database read cannot replay sessions.
  • A session is valid when revoked_at is null and expires_at > now().
  • scenario_id is one of mid-programme, first-semester-registration, new-student-pass, graduation-ready.
  • Expired and revoked rows are kept (no purge job yet).
  • student_portal_state holds engine state kept outside the record graph (edited profile, resume, portfolio, payment proofs, chat), one row per Demo student.
  • Fixture dates are relative to seeded_at, so the Demo drifts as days pass; reseed with npm run db:reset.

      API->>DB: read all record tables (one read-only snapshot)
    end

    M-->>API: result (+ changed records / student state)
    opt method wrote
      API->>DB: begin · lock portal_meta · revision unchanged?
      API->>DB: upsert / delete changed rows · revision + 1 · upsert student state · commit

Any instance accepts any token and sees the same records because both live in Neon. Edits persist across instances and cold starts, and everyone signed in as the same Demo student sees them. Only the 55 PortalApi methods are callable (404 otherwise); database errors return 503.

  • Never commit .env, Neon connection strings, Vercel tokens, or demo passwords. Local copies sit only in the gitignored control-plane/.credentials/.
  • API logs redact Authorization and the login password.
  • Rotate the Neon role (and redeploy) if a connection string leaks; recreate the reader with npm run db:create-reader in db-admin.
  • PoC databases may be wiped; do not store real student PII.

Limitations

  • No CMS: every write is Demo; cms.mode is stub until CAP-53 connects the Cyberjaya CMS.
  • Mock engine: records are in Neon but still run through the student-portal MockPortalApi rules; student state (profile, portfolio, proofs, chat) is last-write-wins per student.
  • Date drift: fixture dates are relative to the seed time; reseed with npm run db:reset.
  • No file store: uploads (evidence, assignments, payment proofs) are metadata only.
  • Shared Demo logins: four sample students, passwords held by the team.
  • Free tier: Neon 0.5 GB storage, 50 CU-hours / month, scale-to-zero (first request after idle is slower).
  • Session rows accumulate: no cleanup job for expired / revoked rows.

Why Neon on Vercel

Vercel’s first-party Vercel Postgres is discontinued; databases come from Vercel Marketplace. Neon is the simplest free option: native integration, $0 start, scale-to-zero, branching. Prefer Supabase only if a PoC needs bundled Auth / Storage / Realtime — Raisd’s shape (SPA → Portal API → Postgres) does not.

Graduation path: keep the Portal API contract; move durable data to SDD-12 Postgres on UltaHost (or the CAP-53 CMS adapter). Swap DATABASE_URL / CMS adapter — do not teach the SPA a second data plane.

Out of scope

  • Replacing UltaHost / k3s stages or hostnames (apply.raisd.co, api.raisd.co, …).
  • Moving the existing Cyberjaya CMS onto Neon or Vercel.
  • Staff Live progression APIs (still deferred — GET /v1/meta/staff-progression).
  • Using free-tier Neon as production capacity planning.
