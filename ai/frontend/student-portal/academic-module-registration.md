# Academic Module Registration

## Scope and route

Academic Module Registration is a completed frontend-only route at `/academic/module-registration`. It demonstrates a first-confirmation-only registration and Finance transaction against the replaceable `PortalApi`; it does not connect to a live registry, reserve a real seat, create a database, or persist after refresh.

The route is exercised by Alya Putri's local first-semester scenario and Mei Lin's international new-Student-Pass scenario. Their rolling Semester 1 begins six campus-calendar days after the mock session is created, so the preceding seven-day registration period is open. Alya can confirm under the normal academic rules. Mei retains portal and planning access but cannot request a fee preview or confirm until her exact new-pass case reaches eVAL approval. Rizal's current Semester 4 window is closed and renders the completed registration empty state.

## Credit and eligibility policy

- Programme Version owns a 12-credit minimum and a 20-credit standard maximum for a semester.
- A student-specific exception is a `CreditLoadOverride` tied to one exact Study Period. The active approved maximum replaces only that period's standard maximum. Rizal's historical Semester 3 24-credit repeat load is backed by this record rather than by a global 24-credit rule.
- Candidates combine Curriculum Modules recommended for the selected Study Period's programme-semester number with unresolved failed modules from the same Programme Enrolment. A failed module becomes a `required-repeat` candidate only when the active campus has a Module Offering for it in the selected Academic Term. Any passing Module Result for that Module resolves the requirement and removes it from repeat candidates while preserving the failed attempt in history.
- Eligibility is derived from the student's published prerequisite attempts and the required minimum grade. A recommended module whose prerequisite is still failed remains visible but disabled with the exact requirement; selecting the prerequisite repeat in the same registration does not unlock concurrent registration.
- Confirmation rejects incomplete rows, duplicate Modules, unknown sections, omission of an eligible required repeat, credit totals outside the effective range, and overlapping class schedules. Seat capacity is deliberately not part of the current logical contract; every returned section is selectable unless another registration rule blocks it.
- Confirmation access is derived from the selected student, exact Programme Enrolment, citizenship, campus Immigration configuration, shared current Student Visa / Pass selection, campus-local date, and newest owned new-pass case. Malaysian citizens and international students with a valid or not-yet-expired expiring pass are available. An international student without a pass, or with a cancelled pass and eligible replacement case, requires `eval-approved` or a later new-pass milestone; missing applications, cancelled-pass pre-application state, pre-eVAL states, information requests and rejection remain blocked. A naturally expired pass directs the student to the International Office.

## Open registration experience

The module editor uses shared container-responsive `FormGrid` layouts for mode/credits and schedule metadata. Day, time and location stack at phone widths; column spans reset with the shared grid so they cannot create implicit narrow columns or clip weekday names. The popup body scrolls independently while Save Changes and Cancel remain reachable.

- The pre-confirmation registration summary uses the default subtle `SummaryCard`. Its semantic Semester heading intentionally omits the optional label and action, while Semester Start, Semester End, Semester Duration, and live selected/effective Credit Hours use the divided summary columns. The shared component stacks every summary item one per row on phones and retains content-sized wrapping columns above the phone breakpoint. The shared `CreditLoadBar` occupies the optional supporting-content slot 20px below those columns; on phones its segments take a dedicated full-width row above a left-aligned status row whose indicator remains adjacent to the label. The card owns all padding, dividers, wrapping, label/value typography, and its loading state uses the same slot anatomy with Skeleton content.
- Module Registration, Module List, and Timetable use the shared panel-type `ContentSection` hierarchy. Their stable 36px header rows align titles whether or not an action is present, each keeps a 16px gap to its content, and sibling sections remain 32px apart. Layout-matched loading states reserve the same geometry.
- Alya begins with all five eligible recommended four-credit modules and a viable section selected, totalling 20 credits. She has no previous attempt, so she has no repeat candidate. The first two modules expose alternate sections to prove the separate Module and Class Section controls.
- Module List uses the shared semantic `DataTable` with one single-line row per complete draft. Its columns are Module Name, Code, Section, Lecturer, Mode, Credits, and a neutral trash action. Its `bordered` variant owns the unpadded rounded border and gives only the header row a `surface-raised` background: header cells use 8px padding, body cells use 12px by 8px padding, and the outer columns use 16px edge insets. The table scrolls horizontally only when its columns cannot fit; its final row has no trailing divider, and the numeric Credits column is horizontally centred. Clicking or keyboard-activating a row opens Edit Module; the trash action removes that row without opening the editor.
- The title-row `Add Module` brand button remains visible and is disabled at the effective credit maximum or when no eligible compatible candidate remains. It opens the shared controlled `Popup` with Module and Class Section selectors plus derived read-only Lecturer, Mode, Credits, and schedule fields. Mode and Credits share a 50/50 four-column rhythm; physical Day, Time, and Location use 25/25/50 on the same rhythm. Every recurring Class Schedule for the selected section is sorted by weekday and start time. Physical and hybrid sections show Day, Time, and Location; online sections show Day and Time only. Time remains 24-hour but drops a leading zero for a single-digit hour, such as `9:00–12:00`. Multiple weekly sessions are labelled Class 1, Class 2, and so on; an offering without a schedule shows `Schedule not confirmed`. Add and edit choices stay isolated from the page draft until the popup primary action succeeds; Cancel or close discards them.
- Editing preserves the row's stable draft identity and allows both Module and Class Section changes. Selecting the module already owned by that row preserves its section. Changing to a different module clears the section only when multiple valid alternatives require a choice; one valid section is selected automatically.
- Candidate options place `required-repeat` modules first and append `(Required Repeat)` to their visible label. They disable already-selected modules, unmet prerequisites, timetable-only conflicts, and selections that would exceed the effective maximum. Initial drafts include every eligible required repeat first, then add recommended modules without exceeding the effective maximum. Section labels contain only the stable section code; no seat count or seat-limit rule is modelled. The popup ignores the final minimum-credit and required-repeat rules while assembling one row, but the page confirmation enforces the complete policy. Invalid selections use the shared destructive field treatment and a plain-language message.
- The preview reuses `TimetableCard` in registration mode. It always shows Monday through Sunday and the existing 07:00–19:00 grid. Selected classes use brand blocks; their X action removes the same draft row. Empty periods have no plus or prohibited icon.
- List removal and timetable removal operate on one draft array, so module rows, class blocks, and credit segments cannot drift apart.
- Reset restores the recommended default before the first confirmation. It is removed with every other editing control after confirmation.
- A student waiting for eVAL can still add, edit, remove and reset the same component-local draft. The Semester summary keeps its normal neutral presentation. A separate Student Pass `SummaryCard` explains the current Immigration state and links to Applications. A cancelled pass without a replacement case uses the destructive **Student Pass cancelled** state and links to the Student Pass overview. Confirm Registration remains disabled and the fee-preview query is not started before eVAL. Once a replacement case exists, the existing pre-eVAL, eVAL-approved, and completion presentations apply unchanged. eVAL approval unlocks confirmation without submitting the draft automatically, while the notice remains until physical Student Pass completion; navigating away retains the existing non-persistent draft behaviour.
- Confirm opens the shared `Popup` with the exact modules, class sections, modes, and credits before the primary action runs. A separately loaded fee preview shows aggregated tuition, the registration fee, eligible award credit, campus Service Tax, and final Amount Due. The preview exposes no module-level prices; a layout-matched skeleton or scoped error occupies the same region, and final confirmation stays disabled until the preview validates successfully. The compact total registered load and invoice quote remain grouped in quiet borderless `surface-subtle` `InnerSection` wrappers; popup totals are not standalone `SummaryCard` surfaces.
- Confirmation is final for that Study Period. As soon as the mutation succeeds, the page replaces the editable module list and timetable with the shared subtle `EmptyState`: a check icon, `Registration completed`, confirmation and invoice-created copy, and one `View Study Plan` link. Finance remains available through the persistent sidebar.

## Mutation and downstream flow

`PortalApi.getAcademicModuleRegistration()` returns the student, programme, semester, Study Period, timezone, effective policy, validated confirmation-access code/flag/reason, recommended or required-repeat candidate type, prerequisite state, exact offering alternatives, lecturer assignments, all recurring schedules, and any existing confirmed registrations. It derives unresolved repeats from Module Registration and published Module Result history and does not return section capacity, remaining seats, or module prices.

`PortalApi.getModuleRegistrationFeePreview` (`POST /v1/portal/getModuleRegistrationFeePreview`) accepts the Study Period ID plus selected Module Offering IDs and returns only aggregated tuition, registration, gross total, eligible award credit, Service Tax, final amount due, and currency. It first re-evaluates confirmation access against the live canonical graph, then resolves the active enrolment's Finance Account, Programme Version Fee Plan, explicit module-owned tuition Fee Items, one registration Fee Item, funding benefits, citizenship/exemption evidence, and effective campus tax profile. Confirmation recalculates the same access and values rather than trusting the read model or preview.

`PortalApi.confirmModuleRegistrations` (`POST /v1/portal/confirmModuleRegistrations`) is accepted only when the period has no registrations and no conflicting tuition or registration invoice. The mock adapter validates the full academic and Finance ownership chain first, then stages Module Registrations, deterministic tuition and registration Invoices, internal lines, capped award-linked credits, one immutable Service Tax decision per invoice, and the resolved Module Registration issue. The invoice totals are tax-inclusive. The staged canonical graph is fully validated before it replaces the live session graph, so any failure leaves Registration and Finance unchanged. It atomically reserves two consecutive globally unique `INV-######` numbers after the graph's highest issued suffix, assigning tuition first and registration second; the standard Alya flow therefore uses `INV-000019` and `INV-000020`. `INV-000000` is reserved, preview-only placeholders are never issued, and a malformed, duplicate, or exhausted sequence fails without changing the graph. `issuedAt` is the prototype tax point and canonical hidden `dueAt` is the registration closing timestamp. A production backend must provide concurrency-safe permanent invoice-number allocation.

TanStack Query invalidates Registration, Dashboard, Academic projections, both Materials list and exact-item queries, Study Plan, Personal Profile, Finance, Calendar, Community and Chat, Online Forms, and Graduation through one tested dependency registry. As a result, selected modules and class schedules appear immediately, Study Plan gains the registered credit load and Finance state, exact Module Offering community groups become available, the registration issue resolves, and a positive generated balance derives one Outstanding Fees issue. Module Summary, upcoming Materials, and empty Attendance routes are valid after registration.

This mutation is session-only. A new `MockPortalApi`, refresh, or browser restart restores the original unregistered Alya fixture. Development student-view switching retains the canonical registration in the current portal session while clearing scoped queries. The staged write captures student, session generation, and write revision before asynchronous work; a scenario change or same-session concurrent write rejects the stale commit without issuing registrations or invoices. The future HTTP adapter must preserve the same UI contract while the backend owns authorization, concurrency, audit, and persistence. Seat limits may be introduced only through a later approved contract change.

## Closed and missed states

Preview and confirmation read the live transaction clock independently of the fixed fixture-generation date. The opening and closing instants remain inclusive, matching the page phase; requests immediately after closing are rejected even if the session began while registration was open. Registration and Invoice timestamps capture the actual confirmation instant.

Timetable conflicts require overlapping time slots, intersecting inclusive teaching dates, and a shared weekday occurrence within that intersection. Adjacent time slots and sequential teaching blocks are compatible. The page and API use the same predicate.

Confirmation preserves saved Personal Profile fields, emergency contacts, existing chat conversations/messages, deletions, and read markers while updating derived issues and adding eligible module groups. Both chat list and detail queries are invalidated.

- A confirmed registration always renders the same completed `EmptyState`, whether the registration window is still open or has closed.
- A closed period without registrations uses the same `surface-subtle` `EmptyState`, showing **Registration missed** and naming Academic Registry as the owner. When the validated Academic Community service is available, the state provides **Open Academic support** and opens that exact conversation. If Community cannot provide it, the same action slot explicitly says that Academic Registry contact is unavailable in the portal and directs the student to a campus-supplied external contact channel; no no-op button is shown.
- Before opening, the recommended draft is read-only and the opening date is shown.
