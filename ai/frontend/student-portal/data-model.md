# Frontend Logical Data Model

## What this model is

The data model is a version-controlled description of information required by the frontend. It is intentionally independent of database technology. The future backend may use one database, several databases, existing CMS tables, or service calls as long as the Portal API fulfils these contracts.

Open `/dev/data-model` during local development to inspect the live model. The explorer is rendered from the same registry used to validate field metadata and relationships.

## Status vocabulary

| Status        | Meaning                                                |
| ------------- | ------------------------------------------------------ |
| `mocked`      | Used by the frontend with development fixtures.        |
| `confirmed`   | Agreed with the future API/backend team.               |
| `unconfirmed` | Required or assumed by the UI but not yet agreed.      |
| `derived`     | Calculated by the frontend from other contract fields. |

All server-facing records use `Portal API` as their frontend source. Explorer ownership describes the logical business domain and record scope, not a mandated database. For example, Staff Member is institution directory data; it is not fetched from the student's private profile even when a lecturer appears on the student's module screen.

## Canonical aggregates and read models

CAP-51 adds campus-owned `onlineFormDefinitions` and student-owned `onlineFormSubmissions`. Definitions version their ordered typed fields, category, reviewer department, eligibility, and optional evidence kind for upload fields. Context responses expose selected-student evidence references keyed to the form field. Submissions reference the exact Programme Enrolment and optional Module Registration or Student Visa / Pass; immutable submitted snapshots retain the definition, latest-session prefills, owned-evidence references, answers, embedded replacement-file metadata and selected published-result display information. Status events and ordered case messages are embedded owned records; the Data Model Explorer exposes their relationships and derived summaries.

Student Visa / Pass records explicitly reference their Programme Enrolment so Online Forms can reject a pass belonging to another enrolment. Status distinguishes `valid`, `expiring`, `expired`, and `cancelled`; only cancelled records carry `cancelledAt`, and cancellation retains the original expiry. An enrolment may retain multiple historical pass records but only one valid or expiring current record. A shared selector prefers that current record, otherwise the most recently ended record. The catalogue returns the campus timezone independently of its template collection. Case revisions advance monotonically across changes, allowing the query boundary to reject older responses without replacing newer messages or status.

Online Forms queries expose the catalogue, template context and owned draft/case details. Session mutations save drafts with revision checks, submit once, withdraw open cases, append messages and acknowledge visible reviewer sequences. A catalogue includes derived unread counts without loading thread bodies; navigation counts distinct cases, not messages. Messages do not edit original form evidence. Responses are detached and Zod validated, and stale generations cannot mutate another student's caches. The form adapter reads the existing Personal Profile session overlay for current contacts rather than stale canonical contact fixtures. See [Online Forms](online-forms.md).

CAP-50 adds campus/programme-version `CampusImmigrationConfiguration` records plus enrolment-owned `ImmigrationCase`, `ImmigrationDocumentCheck`, and `ImmigrationCaseEvent` records. A case is `new`, `renewal`, or `cancellation`; cancellation records identify a student, graduation, or university trigger. Exact nullable relationships join the case to its application and medical-result Online Form submissions, Student Visa / Pass, and Finance Invoice. A new case snapshots immutable medical-result metadata from its exact case-linked Online Form after eVAL and before passport handover. Graduation-triggered cases are fee-waived cancellations without a duplicate form or invoice. Revisions and session generations gate staff and Online Forms mutations. `PortalApi.getImmigration (`POST /v1/portal/getImmigration`)` returns one detached route read model with applicability, availability decisions, current pass, joined case detail and medical-form status, a complete derived milestone projection, three to five case-specific step definitions, and the recommended step. Completed cases remain canonical but are excluded from the current-case projection. The Module Registration read model derives a validated confirmation-access code plus an independent Student Pass progress state that keeps the notice visible after eVAL and until endorsement completes; no additional gate record is stored. See [Immigration](immigration.md).

CAP-55 adds canonical campus-owned University Policy records with a fixed category, title, summary and explicit display order. `PortalApi.getUniversityPolicies (`POST /v1/portal/getUniversityPolicies`)` resolves selected student → exact selected Programme Enrolment → campus, returns detached ordered summaries, and never falls back across campuses. An enrolled student at an unconfigured campus receives an empty collection; an unknown student or missing selected enrolment is rejected. Policy bodies, versions, effective dates, acknowledgements and publishing metadata are absent from this catalogue contract. See [University Policies](university-policies.md).

The mock Portal API starts with one canonical record graph that can hold multiple students. It is grouped into six aggregates so related information is understandable without pretending that these are physical database tables:

- **Student Record:** Student Profile (owned by Person), Student Identifier history, Emergency Contact, Academic Qualification, English Proficiency, Student Document, Student Resume, Resume Work Experience, Resume Education, Resume Skill, Resume Recognition, Portfolio Project, Student Visa / Pass (linked to the passport identifier), and deliberately limited Person records.
- **Institution:** Campus, Campus Immigration Configuration, University Policy, Faculty, Staff Member (owned by Person), User Account / Role / Permission / grants, Programme, Programme Version, Academic Term, Grading Scheme, Grade Band, and campus policy (status mapping, academic-status, credit, CGPA, document numbering, adjustment — university default when `campusId` is null).
- **Curriculum:** Module, Curriculum Module, Module Prerequisite, Module Equivalency.
- **Delivery:** Module Offering, Teaching Assignment, Class Schedule, Class Session, Module Week, Module Learning Item, and Module Assessment.
- **Student Journey:** Programme Enrolment (with status events), Study Period (`status` timeline + `academicStatus` Registry status, with status events), Module Registration (with status events), Credit Load Override, Student Credit Transfer, Curriculum Substitution, Attendance Record, Learning Progress, Assignment Submission, Assessment Result, Module Result, Term Result (derived totals), Immigration Case, Immigration Document Check, and Immigration Case Event.
- **Finance:** Finance Account, campus Finance Profile, effective-dated Campus Service Tax Profile, enrolment-owned Education Service Tax Exemption, Fee Plan, Fee Item, Invoice, Invoice Line, immutable Invoice Service Tax snapshot, Invoice Void, Credit Note, Payment, Payment Allocation, Payment Reversal, Refund, Funding Scheme, Student Funding Award, Student Funding Benefit, Student Funding Renewal Condition, Financial Adjustment (with category), and session-only Finance Payment Proof metadata.

Contract version `PORTAL_RECORD_SCHEMA_VERSION = 3`. Campus policy collections (status mapping, academic-status, credit, CGPA, document numbering, adjustment) seed university defaults and resolve campus overrides with effective dates. Reporting helpers and matching Postgres views define latest valid study period, current active students, credit summary and outstanding balances — academic-status membership uses campus policy. See [canonical-schema-luct-readiness.md](../../backend/canonical-schema-luct-readiness.md).

Dashboard, Academic Context, Academic Performance, Academic Modules, Academic Study Plan, Profile, Calendar, community, and messaging responses remain smaller route-facing read models. Every student scenario uses the same selected-Programme-Enrolment canonical projections; differences live in records instead of scenario-specific service branches or static route DTOs. Messaging adds a normalized session record set—Conversation, Conversation Participant, Message, and Attachment—joined to the selected scenario's canonical community identities and groups.

The session-only academic completion transition stages final Assessment Results, Module Results and one Term Result against the exact final current Study Period. It validates complete earlier periods, exact result ownership, curriculum passes, earned-credit and CGPA thresholds, and the whole canonical graph before returning a replacement graph. On success, final Module Registrations, the retained Study Period and Academic Term become completed and the owning Programme Enrolment becomes completed. “No current semester” is therefore derived from the absence of a `current` Study Period; the final period is not deleted, so completed-student Performance, Modules, Study Plan and Graduation reads retain the full history.

Module Lecturer read models retain `moduleOfferingId` and `semesterId` alongside the Module and Lecturer IDs. The Data Model Explorer exposes both relationships so historical and repeat teaching assignments cannot collapse into one module-level lecturer. Timetable and attendance projections follow the student's exact registered offerings; attendance joins the owning registration and class session together. Canonical records own the co-lecturers shown in current module cards and Community.

All date-only contracts share real Gregorian calendar validation, including leap years, month ends, and rejection of day zero. Issuance timestamps are converted to the enrolment campus timezone before resolving effective Service Tax profiles or exemptions. Mock fixture creation retains a fixed reference instant, while transaction validation and submission/issuance timestamps use the current clock. Tests can inject that live clock independently of fixture generation.

The Explorer opens on a database-style Records view. Each logical table shows the actual validated mock rows, columns, primary/foreign-key hints, row counts, and clickable foreign-key values. Student filters isolate the private and transactional rows reachable from Alya or Rizal while leaving shared institution, curriculum, staff, and delivery tables visible. Fields, Relationships, Student Timeline, and Row JSON remain available alongside Records. The table names and layout are an integration aid, not a mandated physical database design.

Navigation definitions and design tokens are frontend configuration, not database entities, and therefore do not appear as tables.

Academic Module Registration is also a route-facing read/mutation model derived from the canonical Programme Version, Study Period, Curriculum Module, Module Prerequisite, Module Offering, Teaching Assignment, Class Schedule, Module Registration, Module Result, Grade Band, Credit Load Override, and Student Account Issue records.

Registration candidate derivation also reads Grade Band and published Module Result records. Within the active Programme Enrolment, a Module with at least one failed result and no later or alternative passing result is unresolved. If that Module has a current-term campus offering, the route projects it once as a `required-repeat` candidate before the recommended semester candidates. A passing result suppresses the repeat even though the failed attempt remains in history. Recommended dependants of an unresolved prerequisite stay in the response with `prerequisite-not-met`; a repeat selected in the same draft does not count as a completed prerequisite.

## Campus Services

Sections optionally use composed headings and recursive `stack`/two-child `columns` groups. Typed leaves include headings, paragraphs, lists, notes, photo/dish/icon image groups and rectangular tables. Campus-owned layout fields control cover position, stretching, narrow-container ordering, dividers and table column proportions. Nested block IDs remain unique within each page. Standard blocks without layout options retain their default rendering. The optional contact image carries the same validated media metadata as page content. These fields pass through the existing detail projection; no endpoint, relationship or cache-key changes are needed. The explorer examples are derived from the same canonical records and include the nested content.

Campus service information is a separate institution aggregate described in [Campus Services](campus-services.md). `CampusServicePageRecord` owns structured sections, local image metadata, a campus-unique slug and navigation order. Image metadata may carry validated responsive variants with source paths and dimensions, shared by banners and body media. A catalogue page may deliberately use a null image and empty sections while approved campus content is pending; the portal renders the common banner fallback and Services empty-content state. One optional `CampusServiceContactRecord` belongs to each campus for API compatibility; Services no longer renders contacts and its fixture image is null. Cyberjaya publishes six source-backed categories plus the Accessibility Support placeholder, for seven entries in total; Accommodation and Services Finance are not catalogue records, while student Finance remains separate. The read-only catalogue and page endpoints follow the exact selected Programme Enrolment, return empty collections for unconfigured campuses, and never substitute another campus's data. `ServiceSummary` is a derived catalogue used by sidebar, tabs and breadcrumb. The explorer includes all seven catalogue rows, both canonical records, campus relationships and field-specific endpoint usage.

Campus Service Page banner appearance is campus-owned structured content: dark/light text and an optional contrast gradient. Defaults normalize to dark text with no gradient. It travels through the existing service-detail contract and explorer sample; catalogue rows and campus relationships remain unchanged.

## Profile Privacy & Security

`CampusPrivacySecurityRecord` contains one optional campus-owned Privacy & Security publication: introduction, nullable review date, ordered information categories and ordered account-security guidance with validated responsive local imagery. The canonical graph validates a real campus owner, unique record IDs, one record per campus and unique nested IDs/display orders. `PortalApi.getPrivacySecurity (`POST /v1/portal/getPrivacySecurity`)` resolves selected student → exact selected Programme Enrolment → campus and returns a validated `PrivacySecurityResponse` with that optional record and a derived ordered portal-access summary. ## Reference student scenarios

The current graph provides four selectable scenarios: Alya for first registration, Mei for a new Student Pass, Rizal for active mid-programme study, and Nadia for completed-study and Graduation history. Materials projects canonical weeks, file metadata, assessments and learning transactions rather than maintaining a parallel runtime graph. Resource completion is independent of elapsed teaching weeks. Assignment submission records update in the session graph, including withdrawal timestamps; existing registry relationships and explorer examples describe the same records. Module Attendance follows the selected enrolment's campus/programme configuration. Scenario query keys include session generation and Programme Enrolment, and every write captures the student, generation, and write revision before its asynchronous work. A commit succeeds only when all three still match; stale results are rejected before cache success callbacks with student-facing recovery copy. These changes add no endpoint or persistent storage.

The mock graph contains four deliberately fictional selectable student journeys plus nine directory-quality peer students used to model cross-year community membership. None is copied from a real student, and none may be treated as production data. Alya, Mei, Rizal, and Nadia share the Cyberjaya programme model while owning separate personal, enrolment, study-period, account-issue, academic-transaction, Immigration, Graduation, and Finance records applicable to their lifecycle stage. - Module rosters are derived from the exact Module Offering. Only `registered` Module Registrations and that offering's Teaching Assignments grant current access. A repeat registration is included exactly like a normal registration while active.
- Thomas Hassan preserves a completed failed DMP201 attempt and an active `attemptNumber: 2`, `registrationType: "repeat"` registration in the current DMP201 offering. He is therefore in DMP201 chat but not unrelated module groups.

## Canonical graph integrity

- Every canonical collection enforces collection-local unique record IDs before lookup maps or projections are built. A duplicate can therefore never silently replace another record during validation.
- The academic ownership chain is validated from Campus, Faculty, Programme, Programme Version, Academic Term, Module, and Curriculum Module through Programme Enrolment, Study Period, Module Offering, and Module Registration. An enrolment's campus must own its Programme Version through the Programme Faculty; periods and offerings must use Academic Terms at that same campus; registrations must join a curriculum module offering in the period's exact term and campus.
- A student may have at most one active Programme Enrolment. Historical completed, deferred, and withdrawn enrolments remain valid. Each enrolment may have at most one current Study Period, and Study Periods are unique by enrolment/term and enrolment/programme-semester.
- Offering sections are unique within module, term, and campus. A Study Period can register one Module Offering once, while the same offering can legitimately be shared by registrations owned by different students.
- Attendance joins one registration to a Class Session in the exact same offering and is unique by registration/session. Assessment Results must use an assessment from the exact registered offering; Module Results use a Grading Scheme from the enrolment campus; Assessment, Module, and Term Results each enforce their natural one-result ownership keys.
- All Programme Versions used by the permanent scenarios retain their own Curriculum Module and Module Prerequisite records. The 2024 cohort fixture therefore has a version-owned curriculum instead of depending implicitly on the 2025 rows.

## Change workflow

1. Identify the data required by a screen.
2. Add or change the Zod contract.
3. Update field metadata and relationships in the registry.
4. Add a valid mock fixture and sample payload.
5. Expose the data through `PortalApi` and a query hook.
6. Update this document when conventions or ownership assumptions change.

Compilation and tests must fail when schema fields are missing metadata, relationships point to unknown fields, or fixtures no longer satisfy contracts.

## API conventions

- IDs are opaque non-empty strings.
- Times are ISO 8601 strings with timezone information.
- Missing optional values are represented explicitly as `null` where the UI distinguishes unknown from empty.
- Collections return empty arrays rather than `null`.
- Student-specific API methods use the active scenario's stable `studentProfileId` plus an explicit owned `programmeEnrolmentId`, then traverse that enrolment's Study Period, Module Registration, and Finance Account ownership. They do not depend on a student's position in a fixture array. When a read omits the ID, the shared selector chooses the single active enrolment, then the newest deferred, completed, or withdrawn enrolment in that order; multiple active enrolments are invalid.
- Cross-domain mutations use one dependency registry. Module Registration confirmation refreshes Dashboard, Academic summaries/details, both Materials list and exact-item queries, Study Plan, Calendar, Community/chat, Profile, Finance, Online Forms, and Graduation within the current session scope. Tests execute the invalidation helper against real query-cache keys so a registry entry cannot exist without reaching its consumer shape.
- Attachment sizes use integer bytes; formatted labels are presentation concerns.
- API errors use a stable code, human-readable message, and optional field details.
- Community returns `currentPersonId` instead of a screen-owned current-user guess. Conversation contexts reference an exact Community Group for programme/module chats, a Community Person for personal chats, or a Student Service for service chats.
- `PortalApi.getChatConversations (`POST /v1/portal/getChatConversations`)` is a small summary read model containing context, latest activity, and derived unread count. `PortalApi.getChatConversation (`POST /v1/portal/getChatConversation`)` returns only the active conversation's normalized participants, messages, and attachments. Participant records store `lastReadAt`; they do not persist a second unread counter that can drift from Message records.
- Message send/delete and read-marker changes mutate only the current `MockPortalApi` session. The API rejects self-directed personal messages and group messages from a person who is not in the exact Community Group. A first outgoing personal message creates the Conversation and participant rows; merely opening an empty direct-message screen does not.
- The timetable read model supplies a recurring weekday, campus-local start/end time, and inclusive effective date range. The frontend highlights a current class when the browser machine date, weekday, and campus-local time fall inside that schedule. This is presentation state, not a Portal API field, and it recalculates every minute.
- The canonical Class Schedule owns the recurring pattern. Calendar expands it for the requested campus month and overlays available dated Class Sessions: same-date sessions supply actual times, cancellations remove an occurrence, and off-pattern sessions add make-up classes. Planned offerings therefore appear immediately after registration even before session rows are materialized. Attendance continues to use dated Class Sessions only.
- Timetable class cards use their `moduleId` and `semesterId` to open the matching read-only Module Details offering.
- The timetable renders only weekdays that contain one or more valid scheduled entries; empty weekdays are not shown.
- `CalendarEvent` is a unified monthly read model for classes, assignments, exams, meetups, holidays, and registration periods. It belongs to one Semester and has a nullable Module relationship. Assignment and exam events additionally require the matching `moduleLearningItemId`; other event kinds keep it null. Assignment `startsAt` values are deadlines; Registration uses `startsAt` and `endsAt` for its opening and closing timestamps. All-day event `endsAt` values are exclusive.
- Calendar assignment and exam events use `moduleId`, `semesterId`, and `moduleLearningItemId` to open the exact learning-item detail. Class events open Module Details. Registration events are derived from the selected student's exact Study Period `registrationOpensAt` and `registrationClosesAt`; registrations, meetups, and holidays remain non-navigable because they do not identify a module offering.
- Calendar queries use a validated `semesterId` and `YYYY-MM` month plus the exact selected Programme Enrolment. The response returns the campus time zone, events occurring anywhere within that month, and the referenced modules needed by the agenda. A Registration interval is returned for every month it overlaps and expanded across each covered day in the UI. Class events use the schedule/session overlay above. Released assignment and exam events use the exact Learning Item and Assessment IDs shared with Materials and module issues; future items remain withheld.
- Modules declare an `online` or `physical` delivery mode. Dashboard and Academic Modules cards join ordered lecturer assignments and active module issues through stable IDs. Lecturer avatars are nullable because some source records may not provide one.
- `ModuleOffering` belongs to one Module and one Semester. It provides the summary, credits, optional weekly contact hours, optional classroom type, and optional fee/currency pair used by module details.
- `ModuleAssessment` belongs to one ModuleOffering and supplies its label, category, percentage, and display order. A module-detail response requires at least one assessment and validates that all weights total exactly 100%.
- `StudentAccountIssue` separately identifies active or resolved student-level fees, Student Pass, module-registration, and Graduation Clearance issues; it is not a module-card `ModuleIssue`. Active issues aggregate across every enrolment owned by the selected student so the header count does not disappear while history is selected. Each action carries its owning `programmeEnrolmentId`; the destination switches context before opening the exact Finance, Registration, Immigration, or Graduation Clearance form state. Fee issues may supply `amountMinor` and `currencyCode`; date-based issues may supply `dueAt`. Student Pass actions include the active case's recommended Applications step and live progress so Profile never tells a student to start a case that already exists. The Profile projection reconciles `studentPassRequired`, `expiringVisa`, and `studentPassCancelled` with the shared current-pass selector. Natural expiry remains a destructive expired presentation, cancellation uses its own destructive issue, and a replacement pass resolves the cancelled issue. Module Registration confirmation and Graduation Clearance submission resolve their matching mock-session issues, and an allocation-backed open invoice balance derives one aggregate Outstanding Fees issue.
- Each `ModuleIssue` references both its source `ModuleAssessment` and matching `ModuleLearningItem` through stable IDs; the server should derive it only for an assessment that has been released and remains relevant to the student. Assignment and exam actions use that learning-item ID to open the exact available detail without title matching or frontend ID reconstruction. Module issue countdowns are derived from the assessment's `dueAt` (or exam start) and the owning campus calendar timezone. Resolved issues are retained by the contract but omitted from the cards. The mock schedule is the shared source for Materials, module-card issues, and Calendar assessment events, preventing conflicting dates.
- Programme Version defines six semesters, 120 unique curriculum credits, a 12-credit minimum semester load, and a 20-credit standard maximum. Each prescribed semester contributes 20 curriculum credits. A Credit Load Override belongs to one Study Period and records the approved maximum, reason, approving Staff Member, approval time, and active/revoked status. Rizal's Semester 3 has an explicit active 24-credit override for the additional four-credit ART201 repeat without increasing the curriculum total.
- Programme `totalSemesterCount` defines the chart timeline, so all six programme positions remain visible. The Performance selector contains published terms only. As of 26 August 2026, Semester 4 is ongoing and has no Term Result, Module Result, or Assessment Result; the latest official dashboard and Performance values are Semester 3.
- `TermResult` distinguishes term credits attempted, cumulative transcript attempts, cumulative GPA-counted credits, earned credits, and cumulative points. Semester 3 therefore records 24 term credits and 64 transcript-attempt credits while using 60 credits in CGPA after the passed ART201 repeat replaces the failed attempt for CGPA policy. Both attempts remain visible as Module Results.
- Academic Performance uses `PortalApi.getAcademicPerformance (`POST /v1/portal/getAcademicPerformance`)` read boundary. ## Student Finance

`FeePlan` remains owned by one Programme Version and currency. Each `FeeItem` has a category, label, explicit minor-unit amount, nullable Module relationship, and explicit education-service-tax treatment. Tuition items must reference a Module; registration, books, resource, international-services, repeat-administration, and other items must not. Tuition, registration, resource, repeat-administration, and the general international-services fee are taxable education services in the Malaysian fixture. Books are explicitly exempt; future student-pass or visa items must carry their explicit treatment rather than relying on their label. The current module amounts retain the former RM650-per-credit outcomes as explicit fixtures and are never calculated from credits at runtime.

The canonical ledger keeps module-level tuition `InvoiceLine` records for reconciliation. `PortalApi.getFinanceStatement (`POST /v1/portal/getFinanceStatement`)` derives a student-facing `FinanceStatementResponse` that aggregates all tuition lines on the same semester invoice into one `Semester N Tuition Fee` line. Module codes, names, quantities, and individual prices do not cross the Finance screen boundary. The Academic Module Offering response likewise contains no fee or currency fields.

`PortalApi.getModuleRegistrationFeePreview (`POST /v1/portal/getModuleRegistrationFeePreview`)` accepts one student-owned Study Period plus selected Module Offering IDs and returns only aggregated tuition, the separate registration fee, eligible award credit, SST, final amount due, and currency. `PortalApi.confirmModuleRegistrations (`POST /v1/portal/confirmModuleRegistrations`)` recalculates that quote and commits registrations, both invoices and their lines, eligible award credits, immutable tax snapshots, and issue resolution only after the entire staged graph validates. Every Invoice uses one globally unique `INV-######` number; `INV-000000` is reserved. The mock adapter atomically reserves consecutive numbers after the current highest suffix, while stable opaque Invoice IDs continue to own relationships and routes. Preview-only invoice placeholders never enter the canonical graph or Finance response. A second confirmation, pre-existing target invoice, invalid number, collision, or exhausted sequence is rejected without partial mutation; a production backend must own concurrency-safe permanent numbering.

A Finance Account belongs to one Programme Enrolment and uses one currency. A campus-owned Finance Profile supplies same-currency counter hours, fictional bank details, reference instructions, and expected posting days. An Invoice belongs to the account, gains a category and display title, and has a nullable Study Period so non-semester charges need not fabricate academic ownership. Canonical invoice lifecycle is `issued` or `void`; the response derives `unpaid`, `partially-paid`, `paid`, or `void` from confirmed allocations and invoice adjustments. Canonical `dueAt` remains validated for future use but is frozen out of the student Finance response, status, sorting, and UI.

Student citizenship is stored as an ISO country code alongside the retained nationality display text. `Student Fee Category` is derived relative to the enrolment campus and shown as Local or International, but Malaysian SST eligibility reads Malaysian citizenship directly rather than trusting that display category. An effective-dated Campus Service Tax Profile owns the Malaysian jurisdiction, registered supplier identity/address, SST registration number, rate, currency, and activation interval; campuses and invoice dates without an applicable profile do not charge SST. Non-overlapping profile periods are enforced per campus.

Each Invoice owns exactly one immutable Service Tax decision with a `charged`, `exempt`, or `not-applicable` outcome, taxable base, basis-point rate, tax amount, reason, optional campus tax profile, and determination timestamp. Invoice issuance resolves the effective campus profile, removes explicitly exempt Fee Items, subtracts eligible award-linked credits from their taxable invoice value, applies citizenship or valid full-sponsorship/diplomat evidence, and rounds the remaining 6% tax half-up to the nearest sen. `Invoice.totalMinor` is tax-inclusive and must equal its line subtotal plus the tax snapshot. Later payments, proof submissions, or award-status changes do not recalculate the snapshot. Tax correction documents, filing, and remittance remain outside the frontend prototype.

Education Service Tax Exemption evidence belongs to the Programme Enrolment and records a validity period, fee scope, sponsor/evidence details, and optional Funding Award relationship for fully sponsored fees or diplomat dependants. Malaysian citizenship is a derived exemption and does not require a separate evidence record. Partial institutional award credits reduce the taxable base; a fully covered eligible fee produces no SST and credits remain capped so they cannot create an account credit. These sponsor, diplomat-dependant, and award-netting branches implement the approved prototype policy, not settled production tax treatment: the RMCD Education FAQ expressly treats company-sponsored tuition and institution-funded full scholarships as taxable, so campus Finance or a Malaysian tax adviser must confirm or replace these branches before backend implementation.

A Funding Scheme defines a `scholarship` or `incentive`. A Student Funding Award assigns that scheme to exactly one Programme Enrolment with staff-controlled status, award date, and an ordered start/end Study Period range. Student Funding Benefits belong to that assignment and form a validated union: percentage coverage for one fee category, a fixed same-currency credit for one fee category, or a same-currency informational allowance with frequency. Student Funding Renewal Conditions support only minimum CGPA and minimum semester GPA in this phase. Renewable assignments require at least one condition.

Active fee benefits create invoice-linked credit Financial Adjustments in award-date then stable-ID order. The relationship from an adjustment to its exact Student Funding Benefit makes the credit auditable. Benefit value and invoice collectible balance cap each credit, so stacking cannot create account credit. Allowances cannot be linked to an adjustment and never affect balances. Completed assignments preserve their historical credit links. The student response projects benefits and applied-credit totals while exposing no award mutation.

Renewal evaluation finds the latest published Term Result owned by the same Programme Enrolment. Each condition is `met`, `not-met`, or `pending`; the combined award evaluation is not met when any condition fails, pending when evidence is unavailable, and met only when every condition passes. This read model does not alter the authoritative assignment status, suspend an award, or revoke a credit.

Invoice balances subtract confirmed Payment Allocations and invoice-specific credits, and add invoice-specific debits from tax-inclusive invoice totals. The Finance response exposes their combined open-invoice balance separately from the signed account ledger balance and the unallocated portion of each confirmed Payment. Account balance includes all non-void invoices, all confirmed Payments, and all account/invoice Financial Adjustments. Reversed Payments and pending proof metadata remain visible but do not reduce a balance. Student attention, Study Plan, and Graduation use the open-invoice balance; confirmed money remains unapplied credit until Finance links it to an Invoice. The graph contract verifies fee/tax treatment, invoice subtotal-plus-SST totals, tax profile/exemption ownership, invoice line ownership, allocation limits, adjustment ownership, currency agreement, and student/campus relationships.

A `FinancePaymentProof` is a derived session record attached to one student-owned unpaid Invoice. It stores transfer amount/date/reference plus one validated PDF, JPEG, or PNG filename, MIME type, positive byte size up to 10 MiB, submitted timestamp, and `pending` status. `PortalApi.submitFinancePaymentProof (`POST /v1/portal/submitFinancePaymentProof`)` creates or replaces the one allowed proof; `DELETE` withdraws it. Neither operation creates a Payment or Payment Allocation, changes a balance, uploads bytes, or survives refresh. Development student-view switching retains proofs for the all-student Admin Actions workspace.
