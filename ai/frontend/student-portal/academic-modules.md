# Academic Modules behaviour

On coarse pointers, lecturer review ratings provide five 44px square targets. Below a 30rem review container, the Poor/Excellent endpoints sit above the evenly spaced targets; below 40rem, the controls sit beneath the question. Detail metadata uses the shared stacked `DetailField` treatment in narrow panels.

The Academic Modules routes are frontend-only views backed by `PortalApi.getAcademicModules()`, `PortalApi.getAcademicModuleDetail()`, and the separately loaded `PortalApi.getAcademicModuleMaterials()`, `PortalApi.getAcademicModuleMaterialDetail()`, and `PortalApi.getAcademicModuleAttendance()`. They present the selected Programme Enrolment's registered modules, semester-specific offering details, structured learning materials, read-only attendance, and a session-only assignment-submission demonstration without connecting to a live student-record or learning-management system.

Every list, semester, detail, Materials, Attendance, Calendar entry, and lecturer-review read retains the exact URL-backed `programmeEnrolmentId`. Completed, deferred, and withdrawn contexts may review their owned history, but they never receive current assignment/exam issues or new lecturer-review and assignment actions. Changing programme context returns to the route's list-level state so a semester, module, or item selected under the previous owner cannot leak into the replacement context.

## Page structure

- `/academic/modules` displays the shared `Academic` heading and `TabbedPagePanel` used by Academic Performance.
- The content is ordered as the labelled reusable Semester selector and the Modules panel-type `ContentSection`, with 32px between those major blocks. The selector owns its visible muted label and 8px label-to-control gap. `ContentSection` supplies the stable 36px header row, 16px `type-title` Modules heading, and 16px heading-to-grid gap. The responsive `CardGrid` keeps 16px gaps; cards stay at least 224px wide where space allows, then wrap into additional rows rather than becoming unreadably narrow or overflowing horizontally.
- Every populated semester reuses the existing `ModuleCard`, lecturer assignment, online-class tooltip, and active issue-card patterns from the dashboard. Each card places the module code in the shared spaced muted label style above the module name; its online-class indicator aligns beside that code at the card's top edge. Within the Academic page panel, cards use `surface-raised` while retaining the shared `surface-hover` interaction colour.
- The main action on Module cards in both the dashboard and Academic Modules page opens the shareable `/academic/modules/:moduleId?semesterId=:semesterId` detail route. Assignment and exam issue cards are separate accessible actions and open their exact `/academic/modules/:moduleId/materials/:itemId?semesterId=:semesterId` location. Timetable class cards, Calendar class agenda cards, and the module chat header use Module Details with their stable module and semester IDs. Calendar assignment and exam events use the same exact learning-item route as module issues and Materials. The top-level Academic Modules tab and sidebar state remain active while details are open.
- Academic Performance grade rows remain non-navigable and now expand inline with the matching offering's assessment breakdown; they do not open Module Details.
- The detail content is lazy-loaded inside the existing page panel. An internal `Modules > Module Details` breadcrumb returns to the selected semester's module list.
- Selecting the already-active Modules page tab resets a nested Module Details or learning-item URL to the default `/academic/modules` page. Selecting the active Materials segmented tab from a nested assignment, quiz, or exam view returns to that module's default Materials view.

## Module details

- After the internal breadcrumb, the detail view presents the API-supplied module code as the muted label and the module name as the semantic heading value of the default subtle `SummaryCard`, then shows the shared segmented tabs for Summary, Materials, and Attendance. The heading carries no local typography class because the card owns the 24px `type-section-lg` value treatment. This simple identity combination has no action, description, columns, or supporting content. When there are multiple tabs, a shared-border divider appears only between two neighbouring inactive tabs, preserving a clean active-tab treatment.
- Summary, Materials, and Attendance are implemented. The Summary assessment outline appears after the lecturer cards and before the written summary and module metadata. Materials and Attendance remain separately deferred until their tabs are selected.
- Lecturer cards use the elevated surface, 8px vertical and 12px horizontal padding, supplied avatar and name, and an enabled brand Review action. Review is an intentional frontend-only no-op in this phase.
- The module overview uses shared read-only `DetailField` rows for faculty, programme, credits, weekly hours, learning mode, classroom type, class count, and recurring class schedule. The related rows are grouped in the shared bordered `InnerSection` wrapper. Programme fee items remain internal to Finance and are not exposed in the student-facing Module Offering response or Module Details.
- `SegmentedBar` presents the assessment outline proportionally while keeping each label and percentage visible. The current Graphic Design 3 outline is Quiz 1 (5%), Quiz 2 (5%), Assignment 1 (15%), Assignment 2 (20%), Midterm (20%), and Final Exam (35%). Every segment uses the single opaque `brand` colour; labels, percentages, and relative widths communicate the individual assessment meaning. Only the full bar's first and last coloured ends are rounded; internal segment joins stay square. The outline uses `InnerSection` too.

## Attendance

- Selecting Attendance updates the shareable Module Details URL with `tab=attendance`. Its implementation and query load only while that tab is selected.
- `Attendance Summary` displays four non-interactive shared `SummaryCard` instances on the explicit `surface-raised` tier in the wrapping metric `CardGrid`: Attendance Rate, Present, Absent, and Recorded Sessions. The shared card owns label/value/supporting-copy rhythm, metric emphasis, and value-only semantic colour. Recorded Sessions is Present plus Absent; future `Not taken` sessions are excluded. The rate is rounded from Present divided by Recorded Sessions and uses `success` when it meets the Programme Version threshold or `destructive` when it falls below. With no recorded sessions, the rate displays an em dash and “No attendance recorded” instead of a false 0%.
- `Attendance Calendar` reuses the semester-bounded Attendance calendar filtered to the exact module enrolment/attempt. It retains month navigation, the 8px Present/Absent/Not taken segments, legend, semester boundaries, and current-day label. Module-level day cells are informational status-labelled groups: they have no hover, pointer, selection, selected-day details, or navigation back to the same module.
- Completed/current module offerings show canonical dated sessions. Module Attendance is available only for an actual non-withdrawn registration; future curriculum recommendations do not create offerings or empty module-detail routes. Cancelled sessions stay omitted. The programme-owned minimum attendance threshold remains 80% in the current fixture.

## Materials

- Selecting Materials updates the shareable module-detail URL with `tab=materials`. The Materials implementation and query load only when that tab is selected, preserving the existing deferred Academic and Module Details production boundaries.
- Teaching content uses a single-open Radix accordion ordered by `ModuleWeek.displayOrder`. All weeks begin collapsed, including the week containing the browser machine time; a student opens the relevant week explicitly, and any open week can be collapsed. Each week is one `surface-raised` accordion card with a padding-free disclosed wrapper: expanded learning rows use their own equal 12px insets and shared dividers rather than separate card backgrounds. Completed weeks use the shared green `success` Badge, locked weeks use the neutral outline Badge, and only the current week uses the faded brand Badge. A current or completed week adds one shared 20px warning indicator beside its status when at least one released assessment requires the student's attention; locked weeks never show it.
- Learning rows use category-specific icons: assignment, quiz, and exam each retain their own pictogram. Icon wrappers use the shared `surface-elevated` tier, keeping category identification distinct from the warning/destructive deadline status surface.
- Future weeks remain visible. The list response returns only release-safe identity, type, title, position, and `availableFrom` metadata for a locked item. Instructions, assessment identity, file metadata, rules, deadlines, and locations are withheld until release. Quiz 1 and Assignment 1 therefore appear in the current Week 2 when they become accessible; Assignment 1 can still remain due at the end of Week 4. Its canonical later deadline continues to drive Materials, the module card issue, and Calendar.
- Learning rows distinguish lecture notes, readings, videos, links, assignments, quizzes, and exams with a label and icon. Rows do not carry progress or lock-status pills; week triggers are the single status source and display Completed, Current, or Locked. Assessment labels include their weight in brackets. A released, unsubmitted assignment uses `Due by DD/MM/YYYY`; after submission it uses the green `Submitted on DD/MM/YYYY` state. Released quiz and exam pills use `Scheduled on DD/MM/YYYY`. Locked rows hide these date pills until their API-supplied release time.
- Every released learning row is one full-width keyboard-accessible button with the shared immediate `surface-hover` treatment. Released assignments, quizzes, and exams open their shared detail route. Lecture notes, readings, videos, and external links remain enabled no-op placeholders until their viewing or download workflows are approved. Rows no longer expose separate View or Download icon actions. Locked rows use the same structure but remain natively disabled, muted, and without hover feedback.
- Week attention is derived rather than stored separately. A released assignment remains attention-worthy until its student progress becomes `submitted` or `graded`, including after its due date. A released quiz or exam remains attention-worthy through its scheduled calendar date in the Portal API campus timezone and clears on the following campus date. Resources never create an alert. Multiple qualifying items still produce only one indicator on their week trigger, and the existing minute-updating machine clock refreshes the result without a page reload.
- Exact item URLs load through `getAcademicModuleMaterialDetail()` rather than resolving content from the list payload. Before `availableFrom`, that boundary returns a typed locked result containing the same release-safe metadata, and the page keeps the module shell and Materials breadcrumb while showing a neutral `SummaryCard` with the release time. After release, assignment, quiz, and exam details use the established breadcrumb, `InnerSection`, and read-only `DetailField` patterns. Foreign, unknown, and unowned item IDs remain unavailable.
- `AssignmentSubmissionPanel` demonstrates one-file submission without persistence or upload. It accepts one PDF or ZIP up to 50 MiB. Its submitted filename and timestamp remain on the left, while the text-only actions are right-aligned inside the same `InnerSection`; on phones the actions move below the metadata and fill the panel width. There is no redundant submission-status pill. Change submission and Delete submission use the shared secondary Button; the Popup's final Delete submission confirmation uses the shared primary Button. Deletion awaits the mutation, prevents duplicate dismissal while pending, closes only after success, and otherwise keeps the submission and dialog visible with an accessible error so the student can retry. From `availableFrom` inclusive until `dueAt` exclusive, the student may submit, replace, or confirm deletion. At the exact due time the controls lock; submitted metadata remains visible but cannot be changed or deleted.
- A successful session submission changes the Materials deadline badge to green and removes the corresponding assignment issue from dashboard and Academic Module cards after query invalidation. Deleting before the deadline restores both due badge and issue. Refresh creates a new `MockPortalApi`, so all assignment submission state returns to the fixture default.

## Semester flow

Module Lecturer read models carry the exact `moduleOfferingId` and `semesterId` of their canonical Teaching Assignment. The all-semester Modules response aggregates Teaching Assignments and Staff Members from every owned offering it returns, including historical-only lecturers; it never derives that list from only the active semester. Semester cards and Module Details then select lecturers from the exact offering, so repeat attempts retain their own teachers. Historical Module Details project their own recurring schedules instead of filtering the current Dashboard timetable. The existing GRD301 and DAN201 co-lecturer assignments are canonical records and also participate in Community membership.

- The list is student-scoped through the active Portal API scenario. Alya can inspect all six programme semester positions but has no module Enrolments before her first registration is submitted, so every selection returns the shared illustrated empty state. After session confirmation, only the selected Semester 1 Module Offerings become her module cards and valid Summary, Materials, and Attendance routes; institution-owned alternatives remain hidden because they are not her registrations.
- `SemesterSelector` uses the shared semester dropdown field, with separate previous and next buttons at its left and right edges for one-step navigation.
- Navigation is bounded by `Programme.totalSemesterCount`; the current programme exposes Semester 1 through Semester 6.
- The initial selection comes from `activeSemesterId` (Semester 4 for Rizal). For a completed enrolment without a current semester, this field is null and the selector opens the latest owned historical semester. Nadia has completed registrations and published results across all six semesters; this does not reopen assignment or registration mutations.
- Selecting a semester updates the list URL. Opening a module and returning through the internal breadcrumb preserves that semester ID.
- Semesters 1 through 3 show completed registrations; Semester 3 includes the second ART201 attempt as a repeat and therefore has a 24-credit overload. Semester 4 shows five confirmed `registered` attempts submitted during the registration week before teaching began. Future Semesters 5 and 6 remain selectable and visually muted, but show no modules because the student has not registered for them. Their curriculum recommendations remain visible only in Study Plan.

## Data model

Materials is projected from the selected student's exact registered offering and the canonical Module Week, Learning Item, Assessment and Learning Progress records. GRD301 has all 14 published weeks. Other existing Rizal offerings also have canonical weeks/resources; Alya's prepared offerings contain weeks with no published items. Only available items expose progress and submission rows. Teaching-week elapsed/current/upcoming badges remain calendar indicators, independent of learning progress.

Canonical assessment IDs now pass unchanged through Summary, Materials, module issues, Calendar links and developer examples. The existing release and deadline schedule is retained in the canonical assessment dates; quiz closing times use their canonical `dueAt`. Teaching-week timestamps are resolved from `startsOn` in the owning campus timezone, including daylight-saving boundaries. No second topic/progress fixture is generated inside the route adapter.

Module-card issue urgency also uses the owning campus calendar timezone. Students therefore see the same Today, days-left, and overdue boundary when they travel or open the portal from a device in another timezone.

Saved numeric assessment links from the former six-assessment fixture remain readable: they resolve by the original unique assessment label within the response's owning offering. New links and mutations use canonical IDs. Foreign-offering, unknown or ambiguous legacy links remain unavailable; the compatibility lookup never selects another student's or offering's records.

Assignment submission/replace/withdraw writes the canonical session Assignment Submission records for the exact module registration. Withdrawal marks `deletedAt` and excludes the record from current submissions; Materials projects submitted state from those records, so the explorer and student response agree. It does not fabricate lesson completion, alter formal results, or introduce persistence. Graph validation rejects missing release weeks, mismatched assessments, duplicate week/item identities and cross-offering learning transactions.

The Academic Modules list response contains the Programme, the programme's dated Semester records, the active semester ID, Enrolments, Modules, Lecturers, ModuleLecturers, and ModuleIssues required by the page. Dashboard, Performance, Modules, Timetable, Module Details, Materials, Attendance, Community, Profile, and Calendar use the same selected-enrolment canonical graph projections for every student scenario; scenario identity never chooses a separate route DTO fixture. The separate detail response joins the selected Programme, Semester, Enrolment, Module, ModuleOffering, Lecturers, ModuleLecturers, TimetableEntries, and ModuleAssessments. Materials and Attendance each have their own response so opening Module Details or Summary does not fetch week-level content, DayPicker, or dated attendance sessions.

- `Semester.semesterNumber` provides the programme-relative position displayed by the selector.
- Route-facing `Enrolment.semesterId` is derived from the canonical Module Registration → Module Offering → Academic Term chain. The canonical record also preserves attempt number, repeat/normal type, and registered, completed, withdrawn, or pending-confirmation state. A future curriculum recommendation is not an Enrolment.
- Withdrawn enrolments are omitted from the displayed module grid. Active and completed enrolments remain visible in their respective semesters.
- Module lecturers and issues are joined through stable module and lecturer IDs. Each issue also carries its source assessment ID and matching learning-item ID, so assignment actions never infer their destination from display text. Resolved issues are omitted by the existing module-card model.
- `ModuleOffering` owns semester-specific summary, credits, weekly contact hours, and classroom type. `ModuleAssessment` owns one ordered weighted segment; the complete detail response must total exactly 100%.
- Current Graphic Design 3 details reuse the canonical online delivery mode, four credits, and Tuesday recurring schedule rather than copying conflicting values from the visual reference.
- `ModuleWeek` supplies the offering-owned date boundaries, stable teaching order, and an actual teaching-topic title. `ModuleLearningItem` is the authoritative full record. `ModuleLearningItemView` is a release-aware union: `locked` exposes only safe list metadata, while `available` includes the type-specific resource, assignment, quiz, or exam fields. Assignment items additionally own brief metadata and the one-file submission policy. `StudentLearningProgress` supplies the server-shaped display state only for an available item; the mock adapter derives submitted state from the current session submission.
- `StudentAssignmentSubmission` records only the current student, assignment item, filename, MIME type, integer byte size, and latest submission timestamp. The mock adapter exposes logical submit/delete methods and never retains the selected `File` contents.
- Materials reuses the offering's existing `ModuleAssessment` records for weights and midterm/final identity rather than duplicating another assessment outline. The mock's one canonical assessment schedule derives each learning item's release/deadline data, active `ModuleIssue` records, and Calendar deadline events. Response validation rejects mismatched offering, week, assessment, ordering, timing, and progress relationships.
- `PortalApi.getAcademicModuleAttendance (`POST /v1/portal/getAcademicModuleAttendance`)` returns Module, Semester, the exact Enrolment, campus timezone, Programme Version threshold, and only that enrolment's Attendance Sessions. `AttendanceSession.enrolmentId` preserves repeat-attempt ownership in the route read model. Programme and module attendance reuse one canonical Class Session/Attendance Record projection instead of maintaining separate fixture stories.

## Loading, empty, and failure behaviour

- The completed Modules list tab body is a deferred production chunk. The shared Academic heading, tabs, and page panel render first with a layout-matched semester-and-card fallback, so moving between Academic sections does not pull the list implementation into the eager application bundle.
- After the list body loads, the dedicated query shows its more specific semester selector and responsive module-card skeleton grid while Portal API data is pending.
- API failure shows a destructive but readable page-level error inside the shared panel.
- A valid semester with no non-withdrawn enrolments shows the shared illustrated `EmptyState` with semester-specific copy and never leaves stale cards visible.
- Detail loading uses a layout-matched skeleton. Unknown modules, semesters, and unenrolled combinations show a readable unavailable state with a path back to Modules.
- Materials and Attendance have their own deferred loading skeletons and readable error states. An unreleased exact item shows the neutral locked summary without its content. An unknown, foreign, or unowned nested item and a mismatched module attendance request show a scoped unavailable message rather than falling back to another student's or module's data.

## Scope boundaries

The page does not add attendance editing, appeals, excuses/lateness statuses, functional downloads, production uploads, persistent assignment submissions, quiz/exam start flows, grading, authentication, live API integration, or mobile-specific remediation. Assignment submit/replace/delete exists only as reset-on-refresh mock-session behaviour.

## Lecturer Review — CAP-30

`/academic/modules/:moduleId/lecturers/:lecturerId/review?semesterId=…` remains in the Academic shell with Modules active. Its breadcrumb is Modules → Module Details → Lecturer Review; both return links retain the semester. Like Invoice Details, it replaces the module-detail body rather than repeating the Summary/Materials/Attendance tabs above the questionnaire. Loading and retryable unavailable states remain inside the same shell.

The Review action opens a lecturer photo/name/faculty header and six questionnaire sections matching the supplied design. All 15 ratings are required (1 Poor, 2 Fair, 3 Good, 4 Very good, 5 Excellent); feedback is optional and limited to 2,000 characters. Incomplete submission focuses the first missing rating. The shared Popup confirms that submission cannot be changed; Cancel retains answers and returns focus, and errors permit retry. Native radio groups support arrow keys and a single tab stop per question. Submitted answers render readable rating labels, written feedback and a campus-timezone timestamp, with no editing/deletion. The card changes to View Review.

The campus-owned versioned questionnaire and immutable submission live in the canonical graph. `PortalApi.getLecturerReview()` and `submitLecturerReview()` resolve selected student → programme enrolment → study period → module registration → offering → teaching assignment → staff/faculty/campus. The response carries availability and the exact lecturer. Module Details projects matching review action summaries. The restored `lecturer-*` aliases and canonical `staff-*` IDs resolve against real staff records before assignment authorization; they cannot produce duplicate reviews.

Only an active programme enrolment's current study period and registered module permit new reviews. There are no invented opening/closing dates. Completed semesters cannot receive new submissions, but existing submissions remain viewable. Co-lecturers and repeat/module attempts are independent. Missing campus questionnaires never fall back to Cyberjaya. Submissions validate all question IDs and integer ratings, reject changed questionnaire versions and duplicate submissions, and snapshot the complete questionnaire. Later content changes do not rewrite historical answers.

Drafts use the generation-scoped query cache with no browser persistence; leaving and returning retains them until submission, refresh or scenario replacement. Mutation success updates the review and invalidates Module Details; stale-session completions cannot populate another session. Backend authorization, durable storage, confidentiality policy, staff reporting and general course surveys remain separate work. CAP-28 (marks/lecturer feedback) is unaffected.
